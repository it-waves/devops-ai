Lesson 111 of the DevOps Engineering Bootcamp: monitor Tomcat's health and recover from a failed deployment. A home page that loads is not proof that an app works. You write a health.sh script that checks a /cart/health.jsp endpoint and exits 0 only on status 200, watch it in a loop, then ship a bad release 2.0 on purpose. The health check turns 503 while the home page still says CloudCart 2.0. You read why in the Tomcat log (the setting pool.size is missing), roll back to release 1.0 by copying the old war file back, add the missing setting to data/db.properties and ship 2.0 again until it is healthy. A full screen Chrome recording compares the normal home page with the failing health page.

Get the lab: github.com/it-waves/devops-ai, in academy/lab (lab111.sh and shortcuts111.sh). Install with: sudo install -m 755 lab111.sh /usr/local/sbin/ then run lab up, lab check and lab down after loading the short name with: source shortcuts111.sh. You need any Linux machine with root, a JDK (including the jar tool) and curl (for example: sudo apt install -y openjdk-21-jdk-headless curl), internet access, about 1 GB of free memory and ports 8087 and 8097 free. No systemd is needed. The first lab up downloads Tomcat 10.1.34 from archive.apache.org (about 14 MB). lab down stops Tomcat and removes everything. Only run it on your own machine.

Honest notes: the terminal and the full screen Chrome segment are one real, continuous recording with real Apache Tomcat 10.1.34. The lab was run end to end: it passes 0 of 5 at the start and 5 of 5 after the tasks, and lab down leaves nothing behind. The failing release is a small demo app built by the lab to fail on purpose. The narration is synthetic speech. The hook, steps, task, rubric and recap screens are labelled illustrations, not captures. Your own run is unverified until you do it.
